    Router table¶

    3 router modes BLIS does not host, each mapped to the policy of llm-d's router that stands closest to it, in routers/.

    BLIS hosts one router, llm-d's, and never simulates another (X4). A benchmark run measured behind another router, such as Dynamo's, is scored by simulating the llm-d policy this table names, and the point says so: it names the router the run used, the policy BLIS used and the evidence below, and it is never graded G1 and never presented as if llm-d had routed the run (point-record kind router_differs). This is design §11.3 and §11.4. A router mode with no entry, or an entry whose policy is none, stays not scored (router_unsupported). An entry whose policy is none records that the mode was examined and no policy is close enough, and says why and what would change that.

    An entry whose policy is not none also states each way the mode and the policy differ, each citing the code that shows it, and a measured bound: the largest ratio between the policy and its alternatives for each figure, with the regime it was measured in (workload kind, concurrency range, model, hardware, pool shapes), the evidence file by hash, and what the bound does not cover. The bound is a sensitivity of BLIS's own prediction to the choice of policy. It is not an error against the router's real behaviour, which no run measured. A point scored with the entry copies the differences and the bound, so a reader can decide, figure by figure, whether the substitution is small enough. How the ratios are measured is in the router sensitivity guide.

    An entry is added only with evidence: for each field it states, a citation of the router's own code or documentation at a pinned commit, and a citation of llm-d's router code that the policy rests on. A mapping is bound to the builds of the router the entry lists (revisions): a run on another build of the same router and mode has no mapping and stays router_unsupported. The table is keyed by the router, its mode and its session-affinity setting, not by the framework's label, because a router's behaviour is set by its mode. An entry's file is named for its key, <router>-<mode>, with -affinity-<seconds> when the setting is set, so one key cannot be stated twice. Design §11.4 keys it the same way: by the mode and session-affinity setting a run used.

    Entries¶

    dynamo-kv¶

    Dynamo's kv mode scores each worker by a cost, overlap_score_weight times the blocks of the prompt the worker has not cached plus the decode blocks the router tracks as active on it, with weight 1.0 and temperature 0 by default, so the lowest cost wins and a tie goes to the smaller prefix tree. Both terms are the router's own accounting, fed by the workers' KV events, and the router can hold a request in a queue of its own when the workers are busy (router_queue_threshold). No policy in the closed list does this. least-active-requests reads the router's own in-flight counts but has no prefix term. default adds a prefix term but weighs queue depth and KV-cache utilisation, which llm-d's router reads from its endpoints' metrics, as normalised scores summed with weights 2, 2 and 3, and takes the maximum; Dynamo's cost is in unnormalised block units with the two terms equally weighted per block. The sweep behind the other entries shows the policies that read load differ from each other by up to 1.70 (balanced) and 1.79 (decode-bound) in median time to first token at 64 to 256 clients, default against least-active-requests, so the choice among them is not a rounding. It has no prefix shared between requests, which is the term this mode exists for, so no bound on a stand-in for it can be measured with it. The mode stays unsupported until a composition that carries both terms is hosted and measured on a workload with shared prefixes. A run with session affinity configured is a different key and has no entry.

    The router

    • ai-dynamo/dynamo@1682167d3c97:components/src/dynamo/common/configuration/groups/router_args.py:77-84, for the mode: The frontend's router-mode argument accepts kv among its choices, so a recipe can run it.
    • ai-dynamo/dynamo@1682167d3c97:lib/kv-router/src/scheduling/selector.rs:136-143, for the policy: The cost of a worker is overlap_score_weight times its uncached prefill blocks plus its decode blocks, in block units, unnormalised.
    • ai-dynamo/dynamo@1682167d3c97:lib/kv-router/src/scheduling/selector.rs:271-311, for the policy: At temperature 0 the lowest cost wins and a tie goes to the worker with the smaller prefix tree; at a positive temperature a worker is sampled by softmax.
    • ai-dynamo/dynamo@1682167d3c97:lib/kv-router/src/scheduling/config.rs:284-312, for the policy: The defaults are overlap weight 1.0, temperature 0, router-tracked active blocks, router-tracked prefill tokens and a router queue threshold of 4.0.

    llm-d's router

    • inference-sim/llm-d-router@b1ab0ff7c0b8:pkg/epp/config/loader/defaults.go:49-90, for the policy: The default configuration sums three scorers, queue depth (weight 2), KV-cache utilisation (2) and prefix cache (3), in one profile with the max-score picker; no scorer there reads the router's own cost of blocks.

    dynamo-random¶

    Dynamo's random mode and llm-d's random picker do the same thing: for each request, draw a uniform random index over the available workers, with no state between requests and no reading of load. Neither keeps a counter. llm-d's round-robin policy also picks at random among tied endpoints, so the two llm-d policies choose alike; Dynamo's random mode has no dependence on the order of the worker list. The remaining differences are the source of the randomness and the pools each draw serves, below. How far the choice of policy moves BLIS's figures is the bound; the first group of ratios is against round-robin, the other policy that ignores load, and the second against the policies that read load.

    Differences

    • draw: Dynamo draws a random 64-bit value from the thread's generator for each request and takes it modulo the number of available instances (push_router.rs 379-392). llm-d's picker shuffles the candidates with the hosted runtime's random source and takes the first (random/picker.go 94-97, common.go 98-104). Both are uniform over the workers and independent between requests. BLIS's source is seeded from the run's seed, so a run is reproducible and is one draw of the sequence; Dynamo's is not seeded, and two runs of it differ in the sequence even on one arrival pattern. (citations 2, 4, 5)
    • pools: Each pool draws on its own in both: Dynamo's prefill and decode routers are separate objects (random keeps no counter to share), and llm-d's random picker draws once for each pick of each profile. No shared state couples the prefill and decode picks. (citations 2, 4)
    • frontends: Several frontends do not change the mode: independent uniform draws merged are still uniform, so Dynamo's mode is the same however many frontends a deployment runs. Nothing here differs on that account. (citations 2)
    • load-blind: Neither reads load, so neither reacts to a worker that falls behind. A policy that does (least-active-requests, default, queue-scorer) is not this mode; the second group of ratios in the bound is what a wrong guess of the mode would cost. (citations 2, 4)

    dynamo-round-robin¶

    Dynamo's round-robin mode rotates strictly per request: it takes the next value of a counter and indexes the list of available workers by it, so successive requests go to successive workers and every worker gets the same number to within one. llm-d's round-robin policy does not rotate: it is the max-score picker with no scorer, every endpoint is tied, and the picker chooses among the tied endpoints at random (the hosted scheduler shuffles the candidates before each pick), as the random picker does. Neither reads load, so neither reacts to a worker that falls behind, and over a run both spread requests over every endpoint. They differ in the order: Dynamo's is a cycle and llm-d's is a random draw. The nearest llm-d policy picks at random among tied endpoints, and the random picker is equally close, so the first group of the bound is against it. How far the choice of policy moves BLIS's figures is the bound: small for time per output token and for throughput in most of the regime, large for time to first token at 64 to 256 clients when the alternative reads load. An earlier version of this entry held that no policy was close enough because llm-d's counter, drawn at every pick of every profile, would give a prefill pool of even size every other endpoint. The router's own tests and BLIS runs do not show it (the pool-balance difference), and the argument is not made here.

    Differences

    • strict-rotation: Dynamo rotates strictly per request (push_router.rs 357-372): the n-th request goes to the instance at n modulo the number of available instances. The nearest llm-d policy picks at random among tied endpoints: the max-score picker rotates the tied candidates by a counter, but they reach it in a seeded random order in a hosted runtime, so the choice is uniformly random, and tests of pools of two, three and four reach every endpoint in near equal counts and not in a cycle. The router has no policy that rotates strictly. The random picker is equally close, and the first group of the bound is against it. These statements are about inference-sim/llm-d-router at commit 03246be994224ef031dfdafb966c54f60d01e933 and no other release; the policy list states none of them. (citations 1, 8, 9, 10)
    • frontends: A Dynamo deployment can run several frontend processes, each with router objects and counters of its own that start at zero, so the sequence of requests a worker sees interleaves independent rotations; the recipes the dashboard read run several (enable_multiple_frontends). BLIS hosts one router and picks at random among tied endpoints. Which frontend a request reaches is the load balancer's choice and is not modelled. (citations 2)
    • pool-balance: Under llm-d's policy a prefill pool is used in full, as the random choice among tied endpoints gives. With a workload that saturates the prefill pool (8,192 prompt tokens, 16 output tokens), round-robin served 25.3 to 27.0 requests per second at 16 to 1,024 clients with two prefill endpoints, against 27.1 to 27.3 under least-active-requests and 13.6 with one prefill endpoint; with four it served 46.3 to 53.3 against 53.6 to 54.4. A pool used through one endpoint would give about half. The 14 percent gap at four endpoints and 16 clients is also seen under the random picker and the default policy, so it is the arrival imbalance of a policy that ignores load. BLIS does not record which prefill endpoint served a request, so the mechanism is not confirmed. The tables are in the guide. (citations 5, 6, 7, 8)
    • load-blind: Neither mode reads load, so neither reacts to a worker that falls behind. A policy that does (least-active-requests, default, queue-scorer) is not this mode; the second group of ratios in the bound is what a wrong guess of the mode would cost. (citations 1, 7)

The tie order a picker rotates is therefore random.
    • inference-sim/llm-d-router@03246be99422:pkg/epp/framework/plugins/scheduling/picker/maxscore/picker.go:108-117, for the policy: The max-score picker rotates each group of equal-score endpoints by a counter drawn once per pick; with the candidates in the random order above, the choice among tied endpoints is random, not a cycle.

    The policies llm-d's router offers¶

    A policy is a composition of the router's scheduling plugins that it runs without code of BLIS's own. The list is closed and holds names only:

    Policy Meaning
    round-robin every endpoint is treated alike
    random-picker an endpoint is picked uniformly at random
    least-active-requests the endpoint with the fewest in-flight requests is preferred
    default the router's built-in configuration when none is given
    none no policy is close enough

    What a policy is made of (plugins, weights, tie handling, source files) changes with the router's release, so this repository does not list it. The router fork owns it; each entry above states the behaviour it relies on and cites the router tree at the build it names.

    The file format, and the rules a validator refuses an entry by, are in the router table reference.
