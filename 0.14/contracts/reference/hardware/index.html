    Hardware¶

    Three schemas describe physical resources: a chip, an inter-node fabric, and the storage classes KV cache can be offloaded to. Every figure in them is a datasheet figure, or one computed from datasheet figures; Provenance says which. A measured correction to any of them is a coefficient and belongs in the registry.

    The chip and fabric keys are in PascalCase, as the catalog's files write them. Each key carries its unit. All three schemas accept the catalog's _comment and _comment_* keys inside each chip, fabric and storage class, and discard them on load. Any other undeclared key, including any other key that begins with an underscore, is an error.

    Chip¶

    A file under hardware/, named by its file.

    hardware/h100.yaml
    Provenance: vendor_spec
FieldProvenance:
  MemoryGiB: "measured:H100 SXM5 80GB HBM3"
TFlopsPeak: 989.5
TFlopsFP8: 1979.0
BwPeakTBs: 3.35
_comment_memory: "MemoryGiB is the device total the CUDA driver reports (torch.cuda total_memory), which is what vLLM v0.31.0 multiplies by gpu_memory_utilization (requested = ceil(total_memory x gmu), vllm/v1/worker/utils.py:539-558), not the datasheet's 80 GB: 85,029,158,912 B = 79.1896 GiB on H100 SXM5 80GB HBM3 (vLLM usage stats 'gpu_memory_per_device': 85029158912, https://github.com/vllm-project/vllm/issues/26836; vLLM start-up logs 'Free memory on device (76.0/79.19 GiB)', InferenceX DeepSeek-V4.1-Flash H100 runs, https://github.com/SemiAnalysisAI/InferenceX/actions/runs/35314892357). Measured, not vendor_spec; the rest of this file is vendor_spec."
MemoryGiB: 79.1895752
_comment_interconnect: "IntraNodeBwGBps is the on-package NVLink 4 link as a per-GPU NOMINAL unidirectional bandwidth in GB/s: 900 GB/s bidirectional datasheet spec => 450 unidirectional per GPU. vendor_spec (bidirectional / 2), NOT measured effective throughput; any measured correction is a per-cluster blis-registry number. The inter-node fabric figure and the intra:inter ratio it feeds (#1530) live with the reusable Network fabric class (networks/ib-400g.yaml), paired with this chip per deployment (a cluster/pool concept, #1662)."
IntraNodeBwGBps: 450
_comment_sm: "SMCount is the count of enabled Streaming Multiprocessors on the GH100 die as shipped in this part, from the NVIDIA datasheet (https://resources.nvidia.com/en-us-tensor-core/nvidia-tensor-core-gpu-datasheet). H100 SXM5 enables 132 of the GH100 die's 144 SMs. The cost model uses SMCount for two things: the per-SM share of peak FLOPs, and the 12-SM derate a Triton-path KV fetch withholds while it overlaps a forward pass (cost model §8.3), which is 9.09% at 132 SMs and 11.11% at 108."
SMCount: 132
_comment_cc: "ComputeCapability is the CUDA compute capability NVIDIA lists for this part (https://developer.nvidia.com/cuda-gpus). A model graph that differs by GPU generation resolves its architecture overlay by the major version, so a chip that states none cannot run such a graph."
ComputeCapability: "9.0"
    Key Type Required Meaning
    Provenance string yes Where the figures come from. One of the provenances.
    FieldProvenance map no The source of a field when it is not the file's Provenance, by field name: datasheet, published, or measured:<device>. A field it does not name has the file's.
    TFlopsPeak number yes Dense BF16 peak, TFLOP/s.
    TFlopsFP8 number no Dense FP8 peak, TFLOP/s. Omit on parts without native FP8. If set, it must exceed TFlopsPeak.
    TFlopsNVFP4 number no Dense NVFP4 (NVIDIA's 4-bit float) peak, TFLOP/s. Omit where the format is emulated rather than native.
    BwPeakTBs number yes HBM (on-package memory) bandwidth, TB/s.
    MemoryGiB number yes HBM capacity, GiB.
    IntraNodeBwGBps number yes On-node bandwidth per GPU, one direction, GB/s. NVLink where present.
    SMCount integer yes Streaming multiprocessors, positive.
    ComputeCapability string no CUDA compute capability, major.minor, such as 9.0 (H100, H200) or 10.0 (B200, GB200). A model graph that distinguishes architectures is resolved by the major version; one cannot be resolved for a chip that states none.
    GPUsPerNode integer no GPUs in one node.
    GPUsPerRack integer no GPUs in one rack, where a rack is a distinct link tier. A multiple of GPUsPerNode.
    IntraRackBwGBps number no Bandwidth between nodes inside a rack, GB/s. Needs GPUsPerRack.

    Fabric¶

    A file under networks/, named by its file.

    networks/ib-400g.yaml, comments omitted
    Provenance: vendor_spec
InterNodeBwGBps: 50
    Key Type Required Meaning
    Provenance string yes One of the provenances.
    FieldProvenance map no The source of a field when it is not the file's Provenance, as on a chip.
    InterNodeBwGBps number yes Bandwidth per GPU, one direction, GB/s: the NIC's line rate in Gb/s divided by eight. Nominal, not measured.
    RDMA boolean no Whether transfers bypass the CPU.

    Storage classes¶

    One file, devices/storage.yaml, names each storage class. The key is the class's name, which scenarios and deployments use. A name key inside a class is accepted and replaced by that key. Comment keys are allowed inside a class but not at the top level of the file, where every key is a class.

    A class is a name and a description, and states no number. What a transfer to or from it costs is a fitted or assumed value, so it is a coefficient and not a catalog fact (design SUB-18): the registry holds offload_tier_<class>_read_rate, offload_tier_<class>_write_rate (bytes per microsecond, equal to MB/s) and offload_tier_<class>_base_latency (microseconds per transfer) for every class on every chip, with the method and the evidence of each, and the kernel's TierTime reads them from the scenario's coefficient sets. A file that still states read_bandwidth_mb_s, write_bandwidth_mb_s or base_latency_us is refused.

    devices/storage.yaml
    # Storage tiers for KV-cache offload: the classes a deployment's offload block may name.
#
# A tier is an identity and a description here, and states no number. What a transfer to or
# from a tier costs (the read rate, the write rate and the fixed cost of one transfer) is not a
# declared fact of a device, so it is not in this file (SUB-18, SUB-3). Every figure this file
# held was one of two things: a fit to one host's measurements (cpu_dram), or a value the
# simulator's authors chose for a class (the rest), with no datasheet, benchmark or other
# source cited for it. A fitted or assumed value is a coefficient, and the coefficient registry
# holds each one scoped to the hardware it describes, with its method and its evidence:
#
#   offload_tier_<tier>_read_rate     bytes per microsecond (equal to MB/s), tier to GPU
#   offload_tier_<tier>_write_rate    bytes per microsecond, GPU to tier
#   offload_tier_<tier>_base_latency  microseconds per transfer
#
# in the registry set cost-model-offload-tiers, written by
# registry/scripts/emit_offload_tiers.py. The kernel's TierTime reads them from the scenario's
# coefficient sets. A tier added here needs those three entries for every catalog chip, and a
# test fails until it has them. A file that states read_bandwidth_mb_s, write_bandwidth_mb_s or
# base_latency_us for a tier is refused.
#
# The tiers were split verbatim from the kv_offload_devices: section of inference-sim's
# defaults.yaml (blis-catalog b20b7f1), added by inference-sim PR #1594 (commit 3673d3655e),
# whose own comment describes them as "representative device classes seeded for the multi-tier
# offload holes (#1588/#1589); operators override per run for their hardware". The tiers are
# classes (an NVMe Gen4 drive, object storage), not specific products, so no single datasheet
# could state them.
nvme_gen4:
  _comment: "A PCIe Gen4 NVMe drive, as a class and not a product. Its terms are the registry's offload_tier_nvme_gen4_* entries, assumed."
nvme_gen3:
  _comment: "A PCIe Gen3 NVMe drive, as a class and not a product. Its terms are the registry's offload_tier_nvme_gen3_* entries, assumed."
sata_ssd:
  _comment: "A SATA SSD, as a class and not a product. Its terms are the registry's offload_tier_sata_ssd_* entries, assumed."
cpu_dram:
  _comment: >-
    Pinned host DRAM, reached across the host link. Its terms are the registry's offload_tier_cpu_dram_* entries:
    the rates were fitted to InferenceX CollectiveX swap_blocks rows on one H100 host (sku h100-dgxc) and are
    scoped to that host as transferred rates, with the floor assumed; every other chip carries the same figures
    as transferred and assumed entries until its own host is timed. The host link's own ceiling is the registry's
    host_link_bandwidth, per chip.
s3:
  _comment: "An object store reached over the network, as a class and not a product. Its terms are the registry's offload_tier_s3_* entries, assumed."
nvme_gen4_raid0_8x:
  _comment: >-
    A DGX/HGX H100 node's local NVMe data volume. NVIDIA's DGX H100 user guide and datasheet state 8 x 3.84 TB
    NVMe U.2 drives in RAID 0 at /raid (PCIe Gen4); the drive model is not public. Its terms are the registry's
    offload_tier_nvme_gen4_raid0_8x_* entries: assumed, scoped to the DGX H100 node, and carried unchanged,
    as assumed, to the other chips.

    Checks¶

    Every number must be finite. Beyond that, a chip is invalid if

    • Provenance is not recognized;
    • TFlopsPeak, BwPeakTBs, MemoryGiB or IntraNodeBwGBps is not positive;
    • SMCount is missing or not positive;
    • TFlopsFP8 or TFlopsNVFP4 is negative;
    • TFlopsFP8 is positive but not above TFlopsPeak; no shipped part has an FP8 peak at or below its BF16 peak, so this is almost always a transcription slip;
    • a peak is a sparse figure entered as dense: TFlopsFP8 is more than 3.5 times TFlopsPeak, TFlopsNVFP4 is more than 3.5 times TFlopsFP8, or TFlopsNVFP4 does not exceed TFlopsFP8 (design SUB-16: catalog peaks are dense figures, and their ratios between data types are the datasheet's; the shipped parts run 2.0 to 3.11);
    • GPUsPerRack is not a multiple of GPUsPerNode, when both are set;
    • IntraRackBwGBps is set without GPUsPerRack;
    • ComputeCapability is set but is not major.minor;
    • FieldProvenance names a field the type does not have, or a source that is not datasheet, published or measured:<device>. A fitted or assumed value is not a catalog fact: it is a coefficient and belongs in the coefficient registry (design SUB-18);
    • a fact the file states has no source: the source of a fact FieldProvenance does not name is the file's Provenance, which must itself be a source, so a file whose Provenance is derived states a source for each fact it records; or FieldProvenance names a fact the file does not state.

    A fabric is invalid if Provenance is not recognized, FieldProvenance is invalid as above, or InterNodeBwGBps is not positive. A storage class is invalid if its name is not lower-case letters, digits and underscores, because the name is the middle of three coefficient names. devices/storage.yaml fails to load if it declares no class, a class with no value, or a class that states a rate or a latency.

    The catalog's convention that each SMCount cites a source in its _comment_sm prose is not checked, here or anywhere else, because comments are discarded before validation. blis-schemas#32 records why it was left out of the schema.

    Why three schemas¶

    A chip's peak rates belong to the die. A fabric belongs to the cluster: the same chip sits behind InfiniBand in one cluster and RoCE in another. Storage belongs to whoever provisioned the node. The cost of a collective that crosses nodes depends on the ratio of on-node to off-node bandwidth, which is a property of a chip paired with a fabric, not of either one. The ratio is therefore a function of both, hardware.IntraToInterRatio(chip, fabric), and not a key in either file.
